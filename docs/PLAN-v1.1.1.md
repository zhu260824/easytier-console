```
│                                     │

│                                     │
│  [恢复默认]                          │
└─────────────────────────────────────┘
```

- 右侧 ↺ 是单条重置（名称恢复默认）
- 名称输入框失焦即保存，不用点确定
- 全部配置存 localStorage

### 实现要点

页面模块改为**列表驱动渲染**：

```js
// 现在：index.html 里写死 7 个 section
// 改为：JS 按配置顺序生成 section，DOM 只留一个容器
const MODULES = [
  { id:'node',  name:'本节点',   render: renderNodeCard },
  { id:'peers', name:'对等节点', render: renderPeersCard },
  ...
];
```

**注意**：拖动模块重排时不能重建 DOM（会丢失表格滚动位置和 sparkline），
应使用 `insertBefore` 移动现有节点。

## 五、需求 5：长时段延迟折线（需后端支持）

### 问题

CLI 只提供**当前时刻**的延迟，没有任何历史接口。要「长时段」必须自己攒数据。

### 方案：后端采样 + SQLite 落盘

#### 数据采集

在 Rust 侧增加一个**独立采样线程**，不依赖前端轮询：

```rust
// 每 5 秒采样一次所有 peer 的延迟
// 前端轮询是 2 秒，但落盘不需要那么密
loop {
    if core_running() {
        let peers = cli_json(&["peer"]);
        for p in peers {
            if let Some(lat) = parse_lat(p) {
                db.insert_sample(node_id, lat, loss, now);
            }
        }
    }
    sleep(5s);
}
```

**为什么用 5 秒而不是 2 秒**：24 小时 × 6 节点 × 每 5 秒 = 约 62 万条。
若用 2 秒则是 155 万条，SQLite 体积和查询压力都翻倍，而 5 秒精度
对「看趋势」完全够用。

#### 表结构

```sql
CREATE TABLE samples (
  node_id  TEXT    NOT NULL,
  ts       INTEGER NOT NULL,   -- unix 秒
  lat      REAL,               -- 延迟 ms，NULL 表示采集失败
  loss     REAL,               -- 丢包率 %
  PRIMARY KEY (node_id, ts)
);
CREATE INDEX idx_ts ON samples(ts);
```

`PRIMARY KEY (node_id, ts)` 天然去重，重复采样不产生脏数据。

#### 数据量估算

| 项 | 数值 |
|---|---|
| 采样间隔 | 5 秒 |
| 节点数 | 6（典型） |
| 24 小时条数 | 6 × 17280 = 103,680 |
| 单条大小 | ~30 字节 |
| 24 小时体积 | **约 3 MB** |

**完全可接受**，不需要降采样。

#### 保留策略

每小时清理一次超过 24 小时的记录：

```sql
DELETE FROM samples WHERE ts < now - 86400;
```

#### 数据库位置

```
D:\easytier-console\data\history.db
```

放在程序目录（便携），不放 AppData——符合你这个程序「绿色免安装」的定位。

#### 新增 Tauri 命令

```rust
#[tauri::command]
fn get_latency_history(node_id: String, minutes: u32) -> Result<Vec<Point>, String>
// 返回降采样后的点，最多 720 个（图表宽度上限）
```

**降采样**：查询 24 小时数据时，按分钟聚合（取平均），返回 1440 个点太多，
再按图表宽度二次抽稀到 ~360 个点。

### 交互

- 点击行任意位置 → 打开详情（但点 IP 仍是复制，点 sparkline 仍是大图，需 `stopPropagation`）
- `Esc` 或点遮罩关闭
- 「复制全部信息」输出纯文本，方便贴到工单里

### 需要新增的数据

`peer-center` 和 `route` 已在 `get_status` 里查了吗？需要检查——若没有要补进
`PeerDetail` 结构，通过独立命令 `get_peer_detail(node_id)` 按需查询，
避免每次轮询都多跑两个 CLI（那是 2 秒一次，会拖慢）。

**这个设计要点很重要**：详情是**按需查询**，不进主轮询。

## 十、需要你确认的点

1. **设置面板采用右侧抽屉，还是居中弹窗？**
   - 抽屉：空间大，适合放配置编辑器
   - 弹窗：更聚焦，但日志/配置放在里面会显局促
   - **我倾向抽屉**

2. **24 小时数据是否需要「导出 CSV」？**
   - 加这个能力很简单（约 30 行），但会多一个按钮
   - 对排查问题很有用

3. **「操作」卡片移除后，「打开目录」放哪？**
   - 方案 A：设置面板顶部小图标
   - 方案 B：设置 → 启动分区里
   - **我倾向 A**

4. **模块改名后，设置面板里的名称是否也跟随？**
   - 若用户把「对等节点」改成「成员」，设置面板里应显示「成员」还是「对等节点」？
   - **我倾向显示改名后的名称**，避免用户困惑
